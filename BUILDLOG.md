# Build log

## 2026-07-24 — Phase 00 done: mock node serves the wire format, codec + golden vectors green

**Tried:** Built Phase 00 — the ~200-line mock node (§6, §7), the highest-leverage code in the project — in `mock-node/` (Node.js, one runtime dep `ws`). Pieces: `record.js` hand-written 32-byte little-endian codec matching §4 exactly (sentinels for absent BME280/temp, `packFlags`/`zoneMask`/`seqLo` helpers, CRC-32 over the first 28 bytes); `crc32.js` (zlib/IEEE); `track.js` deterministic synthetic walk (mulberry32 seed) with a *breathing* HDOP 0.8–3.4, satellite count that falls as HDOP rises, periodic 2D-fix drops (clears `fix_3d`), `trip_start` on the first point, slow battery drain — so the app gets uncertainty to render honestly, never a crisp dot; `server.js` WebSocket that sends one JSON `hello` then broadcasts raw 32-byte binary frames on a shared world clock (all clients in lockstep — "one node, everyone sees the same"), plus a `--replay <file.ndjson>` mode; `golden.js` emits 5 golden vectors chosen for the sentinel/sign-extension paths where hand-written codecs actually drift; `decode-cli.js`; `test/record.test.js` (5 tests: exact width, round-trip, LE offsets, CRC catch, golden decode). All green. READMEs for mock-node/schema/android updated to match.

**Surprised:** The golden fixture wasn't deterministic — `golden.js` stamped `generated: new Date().toISOString()` into the file, so every `npm run golden` dirtied git even when no byte moved. That defeats the whole point of a golden fixture (a diff should mean *the format changed*). Dropped the timestamp; regenerating is now byte-identical run-to-run. Verified.

**Next:** Phase 01 — the Android app against this mock: connect the WebSocket, decode the 32-byte frames with a hand-written **Kotlin** codec (the second half of the "one wire format, two hand-written codecs" plan — its drift is the Phase 05 lesson), and get the dot on a MapLibre map with the accuracy ellipse. The Kotlin codec must reproduce `golden/vectors.json` in its own JUnit suite. Still no hardware; ESP-IDF deferred to Phase 03. Silkscreen band check (433 vs 868) still open, still not blocking.

**Tried:** Three planning decisions, no code. Natural stopping point moved to Phase 03. §9 and CLAUDE.md "Project state" rewritten so a fresh session starts on the mock node, not the toolchain. (3) **Android CLI + Journeys recorded** (§6) as the test/CI harness for the mock phases, with an explicit BLE caveat.

**Surprised:** The mock-first flip doesn't violate the "earliest visible milestone" rule the original hardware-first order was built to protect — a dot moving on a real map screen (Phase 01, mock-driven) is a *stronger* first thing to look at than a blinking LED and an SSID, and it lands with the T-Beam still boxed. The whole hardware-first rationale was "don't front-load a week of pure code with nothing on screen"; the mock node satisfies that better than the LED did. Also caught a stale "C and TypeScript" in the HTML §14/Phase-05 copy — leftover from the PWA era — and fixed it to Kotlin.

**Caveat carried forward:** The 9-client cap is a *connection* limit, not a *good-experience* count — LoRa airtime still saturates around 3 phones at 1 Hz, so past that everyone gets decimated positions and honest queue reasons. And Journeys/Android CLI accelerate only the mockable half: BLE and the foreground-service background sync are still tested against the real board, never a Journey.

**Next:** Unchanged in substance — still no code.
